SYSTEM DESIGN

A. SYSTEM DESIGN
1. High-Level System Architecture
The Warehouse Management System (WMS) is designed using a three-tier web application
architecture composed of a Frontend Presentation Layer, a Backend Application Layer, and a
Database Persistence Layer. This architecture ensures modularity, scalability, and
maintainability across the entire platform.
The system is accessed through a web browser and is structured around role-based access
control (RBAC), which separates the system capabilities for three user types: Master, PIC
(Person-In-Charge), and QC.

Figure 1a — Client & Frontend Layer

Figure 1a: Client & Frontend Layer (React.js + Tailwind CSS)

Figure 1b — Backend & Business Logic Layer

Figure 1b: Backend Layer — Laravel 10 REST API, Controllers, Services & Engines

Figure 1c — Database & External Services Layer

Figure 1c: Database Layer — MySQL 8.0 Table Groups & External SMTP Service

The architecture is composed of the following layers:
•​ Frontend Layer: Built using React.js, this layer renders the user interface for all roles.
It communicates with the backend exclusively through RESTful API calls.
•​ Backend Layer: Built with Laravel (PHP), this layer handles business logic,
authentication (JWT-based), and routing. It exposes a REST API consumed by the
frontend.
•​ Database Layer: A MySQL relational database stores all persistent data including
users, inventory, transactions, and audit logs.
•​ Third-party Integrations: Email notifications are handled via SMTP. Report exports
use DomPDF library.

Within the system, data integrity is enforced at several architectural layers. When a user
submits a transaction (e.g., goods receipt or material request), the system enforces
multi-level validation:
•​ Input Validation: The frontend validates form fields before submission; the backend
re-validates all incoming data server-side.
•​ Role Authorization Check: Every API endpoint checks the requesting user's role via
JWT middleware before executing any business logic.
•​ Data Consistency Enforcement: All stock mutation operations are wrapped in
database transactions to ensure ACID compliance.
•​ Audit Trail: Every state-changing operation records the responsible user, timestamp,
and before/after values in dedicated log tables.

b. Asynchronous Processing & Integrations
Certain operations in the WMS are designed to be asynchronous to prevent blocking the
main application thread:
•​ Email Notification Queue: When a material request is submitted or a goods receipt is
completed, notification emails are queued using Laravel's job queue system and
dispatched asynchronously.
•​ Stock Recalculation: After a stock opname is approved, the stock adjustment
propagation is handled as a background job.
•​ Report Generation: For large data sets, report generation is queued and the user is
notified upon completion.

c. Dashboard & User Interface
The system provides a centralized operational visibility dashboard. A dedicated dashboard
accessible by the Master role provides a consolidated view of all active warehouse
operations, including pending approvals, stock alerts, and recent transaction activity.

3. Interface Mock-up Design
The following section presents the interface mock-up designs for all major screens of the
Warehouse Management System.

a. Login Page
The Login Page serves as the entry point of the system. Users input their registered email
and password. The system validates credentials against the database; upon success, a JWT
token is issued and the user is redirected to their role-specific dashboard.

Figure 2a: Login Page — Authentication & Role Routing Flow

b. Master Dashboard
The Master Dashboard provides a consolidated operational view. It displays key performance
indicators (KPIs) including total active stock, pending material requests, open goods receipts,
and recent stock opname status.

c. Goods Receipt List
This page displays a paginated list of all goods receipts recorded in the system. Each entry
shows the receipt ID, vendor name, receipt date, total items, QC status, and the PIC
responsible.

d. Goods Receipt Detail – Before QC
This screen shows the detailed view of a goods receipt that has not yet undergone Quality
Control inspection. The PIC can view the expected items and initiate the QC process.

e. Goods Receipt Detail – Post QC
After the QC inspection is completed, this screen displays the final reconciliation view.
Accepted items are listed with their updated stock quantities. Rejected items appear with
their reason for rejection and the return record reference.

f. Vendor Return Records
This page manages vendor return records. When goods are rejected during QC and returned
to a vendor, a return record is created and listed here. The Master can review return
frequency per vendor.

g. Stock Alert Rules
This configuration page allows the Master to define stock threshold rules for each product.
When inventory falls below the minimum threshold, the system flags the product as low
stock.

h. Create Stock Alert Rule
This form view allows the Master to create a new stock threshold rule. The Master selects a
product, sets the minimum quantity threshold, and optionally specifies a notification
recipient.

i. Real-Time Inventory Monitor
This screen provides a real-time view of current inventory levels across the warehouse.
Products are displayed in a tabular format with their current stock quantity, minimum
threshold, last transaction type, and last updated timestamp.

j. Settings (User & System Settings)
The Settings page allows administrators to manage user accounts, roles, and system
configurations. The Master can create new user accounts, assign or change roles, reset
passwords, and deactivate accounts.

4. Block Diagram — Level 2 (Primitive Software Functions)
At Level 2, each subsystem is further decomposed into its primitive software functions.
These are the lowest-level operations executed by the system.

a. Log Monitoring Module (Audit & Transaction Log)
Every state-changing operation in the system passes through the audit log module. The
primitive functions include:
•​ writeLog(userId, action, tableName, recordId, oldValue, newValue, timestamp):
Writes a single audit entry.
•​ queryLog(filters): Returns filtered log entries for display or reporting.
•​ archiveOldLogs(cutoffDate): Moves older log entries to an archive table to maintain
performance.

b. Detection Engine (Stock Threshold & Alert Engine)
The detection engine evaluates stock levels against predefined rules after every inventory
mutation. Its primitive functions include:
•​ loadThresholdRules(productId): Retrieves the threshold rule for a given product.
•​ evaluateThreshold(currentQty, minQty): Returns a boolean indicating whether the
threshold is breached.
•​ triggerAlert(productId, warehouseId, currentQty): Creates an alert record and
dispatches a notification job.
•​ resolveAlert(alertId): Marks an alert as resolved when stock is replenished.

c. Response Manager (Approval & Fulfillment Handler)
The response manager handles all approval-gated workflows. Primitive functions include:
•​ getPendingRequests(requestType): Queries pending records from the relevant table.
•​ approveRecord(recordId, approverId, timestamp): Updates the record status to
'approved'.
•​ rejectRecord(recordId, approverId, reason): Updates the record status to 'rejected'
with a reason.

•​ notifyRequester(requesterId, result): Dispatches a notification to the requester.
•​ triggerPostApprovalAction(recordType, recordId): Calls the appropriate downstream
action.
